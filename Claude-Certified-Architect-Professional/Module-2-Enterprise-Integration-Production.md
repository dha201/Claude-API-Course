## 1. Evals as Acceptance Criteria

**Core idea:** an eval (evaluation) is a structured test that checks whether the system returns the expected, accurate output. **Timing matters more than the definition.** Writing the eval suite *before* production code forces three things that are otherwise deferred: (1) state what success means in measurable terms; (2) expose design assumptions early, while changing them is cheap; (3) give yourself a gate that can prove whether a model swap, prompt change, or new retrieval strategy actually improved the system. **If you cannot write an eval for a behavior, you cannot verify that behavior is present** — every change becomes unverifiable.

**How the eval workflow runs (each stage's output feeds the next):**

| Stage | What happens | Output |
|---|---|---|
| 1. Define the task | State the behavior you are evaluating in specific, measurable terms, and write the prompt you will use to test it. A vague definition produces a vague eval. The level of concreteness of both the behavioral specification and the prompt is what makes the result meaningful. | Task specification with prompt to test and pass criteria |
| 2. Build the golden dataset | Assemble the inputs that your system will encounter, including edge cases and counterexamples. This dataset is what your eval runs against. If the dataset is not representative, then the scores are not meaningful. | Labeled dataset with expected outputs |
| 3. Run automated checks | Pass each prompt through the system and compare the output against your expected result. Automated checks are fast and cheap. Use them for behaviors that are unambiguous: format compliance, schema validation, and factual lookups against authoritative data. | Pass/fail record per item |
| 4. Score with a judge | For behaviors that require interpretation, such as tone, accuracy of reasoning, and appropriateness of edge-case responses, a model-based judge can assess the outputs at scale. | Score per item with reasoning |
| 5. Interpret and act | Aggregate scores tell you where the system is and whether a change moved it in the right direction. A change that raises the mean score while quietly degrading performance on edge cases or adversarial inputs doesn't make the system better. | Overall score, per-category breakdown |

**Model-based vs. code-based vs. human-review evals — the three speed-vs-flexibility tradeoffs:**

| Eval type | How it works | When to use it | Cost | Limitation |
|---|---|---|---|---|
| Code-based eval | A function checks the output programmatically: schema validation, regex match, JSON parse, length check, assertion against authoritative data. | Any behavior that is unambiguous. Format compliance, schema correctness, lookup accuracy, length constraints. | Very low: milliseconds per check, no API call. | Can't assess behaviors that require interpretation. Tone, helpfulness, reasoning quality, and edge-case appropriateness all require judgment that a function cannot supply. |
| Model-based eval | A judge model receives the original prompt, the system output, and a scoring rubric. The judge returns a score and reasoning. The judge prompt is itself a prompt that needs to be engineered and tested. | Any behavior that requires interpretation: response quality, instruction following, reasoning accuracy, safety, and handling of ambiguous inputs. | Medium to high: one API call per item evaluated, at the judge model's per-token rate; at scale, this adds up. | Judge models can be inconsistent in borderline cases. Without forcing the judge to produce reasoning alongside the score, that inconsistency is difficult to detect. |
| Human-review | A human evaluator reads the output and scores it against a rubric or set of criteria. This may be structured (a scoring sheet) or unstructured (open annotations and feedback). | High-stakes or novel behaviors where neither a function nor a judge model can be trusted: safety-critical edge cases, new capability areas without established rubrics, or any output where a wrong evaluation carries significant risk. Also useful for calibrating and validating model-based evals. | High: human time is the most expensive resource, and throughput is limited. Not viable at scale without sampling. | Slow, expensive, and not scalable beyond sampled subsets. Human evaluators also introduce their own inconsistency. |

**The grading ladder — reach for the cheapest reliable method first, climb only when the behavior demands it:**
1. **Code-based grading** wherever the behavior allows it (schema, exact match, length, presence) — runs in milliseconds, costs almost nothing, never drifts. *If a behavior can be checked in code, it should be.*
2. **LLM-as-judge** when the behavior needs interpretation — make it rigorous with detailed rubrics, constrained verdicts (a small fixed label set, not free-form scores), calibration against human-labeled examples, and grading with a *different* model than the one being evaluated (to avoid self-preference).
3. **Human grading** as the last resort — highest cost, least scalable.

> **Judge calibration (the step many teams skip):** an LLM judge is itself a system that can be wrong. Before you trust its verdicts, run it against human-labeled outputs and confirm similarity with human judgment is high enough to rely on. An uncalibrated judge produces confident scores that may not be high quality at all — *worse than no automated grade, because it seems trustworthy.* **Favor volume over perfection:** many cheap auto-gradable cases catch more regressions than a small painstaking set, and they run on every change.

**Turning a business requirement into a measurable threshold:** identify the behavior specifically ("summarize claims accurately" → "extract the filer's name, claim number, incident date, and claimed amount from each document"); **set the threshold** from the business requirement, not from what your first prototype happens to hit; **identify the failure modes** (fake claim number, missing incident date, value from the wrong claim — each becomes a category in the dataset); **include adversarial inputs** (missing fields, handwritten sections, unusual formats). *If your golden dataset contains only clean inputs, your eval scores will not predict production performance.* (Threshold-setting guidance: `platform.claude.com/docs/en/test-and-evaluate/develop-tests`.)

**Evals as the gate for change:** every change — model swap, prompt revision, context-strategy change, retrieval-config update — runs through the eval suite during development before production. A **single-turn** eval set won't tell you how the system holds across a conversation; **multi-turn evals** are a separate category scoring the system over a sequence (does it keep prior context straight, answer follow-ups without inventing detail, hold quality as the conversation runs long) and need their own golden dataset of full transcripts with known-good responses at each turn.

**⚠ Watch Out — "the eval suite that measured the wrong thing."** A contract-review assistant was manually tested against ten well-known contracts, declared ready, and shipped; the regression arrived two weeks later on contracts with **non-standard obligation structures** it had never been tested against (the model extracted obligations from the wrong section). Three compounding mistakes: (1) the dataset was built from *convenient* inputs, not a representative sample — so it measured a different system than the one shipping; (2) the input set was **not updated after the prompt changed**, so the eval kept passing while testing behavior the prompt no longer produced; (3) manual spot-checks were treated as an eval substitute — they confirm a specific input's output but say nothing about unknown inputs. **Both defects (unrepresentative + stale) are invisible until production exposes the gap.** *A team that revised a summarization prompt but not its eval suite shipped truncated multi-clause legal sentences two days later — the eval predated the change.* **Rule:** run evals before every change and keep the eval set current with the system it measures.

**Cost · Complexity · Risk:** every model-based eval is an API call, but the bigger risk is *under*-evaluating — size the dataset for confidence and treat cost as secondary. Eval infrastructure is a parallel system to maintain (golden dataset kept current, judge prompts engineered, thresholds revisited). *The highest-risk moment for a regression is when evals are present and out of date* — an out-of-date suite gives false confidence. (Implementation patterns: `github.com/anthropics/claude-cookbooks/blob/main/misc/building_evals.ipynb`.)

> **Checkpoint — Sort the eval types (code-based vs. model-based).** The rule: does the behavior being checked require interpretation (model-based) or is it unambiguous (code-based)?
> - **Code-based:** (1) every response is valid JSON matching the schema; (3) response length under 500 tokens; (5) extracted claim number matches the quantitative value in the source; (7) all required sections (executive summary, methodology, findings, recommendations) present.
> - **Model-based:** (2) whether the model's reasoning in a complex analysis is sound and complete; (4) how appropriately the system handles an emotionally charged complaint; (6) whether the summary captures the most important points of a long briefing; (8) whether the tone of a customer-facing message is appropriately professional for the brand.

## 2. From POC to Production — cost, latency, reliability, failure modes

Your eval suite says whether the system behaves correctly; it says nothing about whether it can **afford** to behave correctly at production volume. That gap has four dimensions — **cost, latency, reliability, failure modes** — all invisible in a demo. A POC also gives the first signal on whether the system moves the **business metric** it was meant to improve; measure that on the POC sample even before modeling cost, because a within-budget system that doesn't move the metric is still a failed deployment.

**Where a POC and a production system diverge:**

| Dimension | Why it's invisible in a demo | What it looks like when it fails |
|---|---|---|
| Cost | A POC running 10–50 requests per day produces a negligible bill. Monthly cost projections at production volume are a different calculation entirely. | The billing dashboard shows a cost that exceeds the budget signed off at project approval. The architecture must be renegotiated after deployment. |
| Latency | A demo typically runs one request at a time. Latency p95 under concurrent load is a different number than median latency under a single request. | SLA breaches and user abandonment. Latency that is acceptable for a demo can be unacceptable for a real-time user-facing workflow. |
| Reliability | A POC has no retry logic, no fallback, and no circuit breaker. When it fails, the developer refreshes and tries again. There are no users waiting. | Without retry logic or fallback handling, any transient API failure takes the entire user-facing workflow down rather than degrading gracefully. |
| Failure modes | A demo is tested on inputs the developer expects. Production raises inputs the developer did not expect. Failure modes are specific to architecture type. | Silent degradation, made-up outputs on edge-case inputs, or complete failure on an input class that was never tested. |

**Cost and latency modeling (built *before* the architecture is finalized).** Three inputs: **call volume**, **token budget per request** (input + expected output), and **model tier** — from these, estimate monthly cost and check it against the ceiling before writing code. *Where most cost models go wrong:* teams take the average token count and assume that is the distribution. Token distributions are usually **skewed** — a tail of long requests consumes a disproportionate share, so an average-based model can underestimate cost by 2–3×. Latency is the same: median reflects the middle, but SLA breaches come from the slow tail, which is why **p95** (the value below which 95% of requests complete) is the design target. **Caching** is the strongest cost/latency lever when the system prompt is long and stable — prompt caching preserves the processed prefix so it isn't reprocessed; if cache reads are charged at ~10% of the standard input rate, a long prefix reused across many requests yields the largest savings. The risk is a **consistency window** if the cached content must reflect live state. (Current cache-read rate: `platform.claude.com/docs/en/about-claude/pricing`.)

**Reliability controls — and where each must sit:**
- **Transient error recovery with exponential backoff** — on a transient error (429 rate limit, timeout, 5xx), retry with progressively longer delays; cap attempts and total wait to what the use case tolerates. *Belongs close to the API call.*
- **Fallback chains** — if the primary model/endpoint is unavailable, route automatically to an alternative (different tier, cached response) rather than raising an error; test fallback in the eval suite. *Belongs in the orchestration layer.*
- **Circuit breakers** — measure the error rate on a downstream dependency and trip when it exceeds a threshold, so requests fail fast instead of waiting on timeouts. *Belongs at the service boundary.*

Placing a control in the wrong layer protects the wrong part of the system and leaves the right part exposed.

**Failure modes by architecture type** (agents handle tasks that can't be done in one call — use tools, observe results, adjust plans, complete multi-step processes; Claude Code is a production example):

| Architecture | What breaks first | Mitigation |
|---|---|---|
| Agent | Unbounded tool use and growing context. An agent that can call tools without budget constraints or turn limits will run up cost and latency in ways that are invisible until a single request exceeds the budget ceiling. | Set per-turn token budgets, maximum tool call counts, and explicit stopping criteria. Constrain the tool set to the minimum required. Eval the agent's stopping behavior, not just its output quality. |
| RAG (retrieval-augmented generation) | Retrieval quality drift. The retrieval layer degrades when documents are added or removed without reindexing, when query and document representation fall out of alignment, or when the index is refreshed on a schedule that creates staleness for live-state queries. | Keep retrieval quality in the eval loop. Monitor retrieval precision and recall as system metrics, not just output quality. Separate live-state queries from static knowledge queries. |
| Document processing pipeline (Evaluator-optimizer) | No exception path for low-confidence extractions. A pipeline that routes all documents through the same flow regardless of extraction confidence will produce wrong outputs on edge cases at the same rate it produces correct outputs on clean documents. | Add confidence scoring to the extraction step. Route low-confidence extractions to a human review queue rather than downstream processing. Include edge-cases and difficult documents in your eval set. |
| Orchestrator-workers | Failure boundaries between orchestrators and subagents blur, traces fragment, and a dropped subagent can fail silently at synthesis. | Define recoverable (subagent: retry or flag) versus unrecoverable (orchestrator) boundaries. Create a shared trace ID across all agents. Reconcile coverage at synthesis so results equal the units submitted. |

> **Model version pinning** applies to *every* architecture above equally — it is an operational discipline, not an architecture choice. Pin model versions in config, monitor the deprecation page (`platform.claude.com/docs/en/about-claude/model-deprecations`), and keep a version-update runbook.

**⚠ Watch Out — "the demo cost profile that became the production bill."** A document-triage team's 60-day post-launch review surfaced three quotes naming one mistake: (1) raw demo costs were presented to the client *without extrapolating to production volume with error bounds* — "presenting raw demo costs without that extrapolation is where risk lives"; (2) they assumed a **uniform token distribution** but the long-document tail consumed 80% of token spend; (3) a **529 error at peak on day three took the whole workflow down** because no fallback was ever tested. The failures compound in order — wrong volume → wrong distribution → untested reliability — sharing one root cause: **the POC was treated as a cost and reliability model when it only answers "can the system do this," never "what does it cost at scale" or "what happens when a dependency fails."** All three are production-system properties a POC establishes none of.

**Cost · Complexity · Risk:** don't assume POC costs match production — model before committing to an architecture, not after the first bill. Retries/fallbacks/circuit breakers are much harder to retrofit — build reliability in from the start. A system with no fallback and no circuit breaker has one point of failure (the primary endpoint); when it goes down at peak, the whole workflow fails instead of degrading.

> **Checkpoint — Cost & reliability calculator.** Scenario: a customer-service agent, 50,000 requests/month, a stable 5,000-token system prompt, ~300-token input, ~400-token output, **$800/month ceiling**, **p95 ≤ 3s**. A configuration on Sonnet with prompt caching on, a 512 max_tokens cap, and 1.0× volume lands at **$720/mo and 2.5s p95** — meeting both targets. *Decision: which lever did the most work?* **Answer: B — turning prompt caching on**, because the 5,000-token system prompt is stable across all 50,000 requests, so caching it cuts the dominant input-cost driver. (Not A — "most capable model is always safest" is wrong; not C — raising max_tokens adds headroom, not savings.)

## 3. Use-Case Sizing & Feasibility

The **production readiness checklist** says what a system must achieve to be viable — output quality (validated by evals) *and* system reliability (validated by architecture controls: retries, fallbacks, circuit breakers). Meeting both bars is what "production ready" means. **Sizing** says whether a specific business problem can meet that bar and what constraints govern the design. Feasibility resolves to one of three states: **feasible as scoped, feasible with constraints, not feasible** — identifying the state correctly is what makes a scoping document useful.

**How to size a use case (a cost model before any code).** Four inputs: call volume, token budget per request, model tier, and sensitivity parameters.
- **Step 1 — Estimate call volume.** Get this from the *business owner*, not developer intuition or a sample dataset. (1,000 conversations/day → 1,000 calls/day plus multi-turn continuations.)
- **Step 2 — Set the token budget per request.** Input tokens (system prompt + retrieved context + user message) plus output tokens. **Model the distribution, not just the average.** If the system prompt is long and stable, prompt caching cuts input cost, but caching requires explicit `cache_control` markers, **cache writes cost more than standard input** (account for the first-use write), and the default cache **TTL is 5 minutes** — workloads with request frequency lower than the TTL won't realize consistent savings.
- **Step 3 — Project the monthly cost.** Multiply volume × input tokens at the input rate, add volume × output tokens at the output rate (input and output are priced differently on all tiers); use the cache-read rate for cached input where caching applies. Compare to the ceiling — **if the projection exceeds it, the architecture changes before a line of code is written.** *Batch API* (if it provides ~50% off standard pricing and supports up to 100,000 requests/batch) is a cost alternative wherever the SLA permits async processing — but for regulated workloads verify batch is BAA-covered before routing PHI. (Rates/limits: `platform.claude.com/docs/en/about-claude/pricing`.)
- **Step 4 — Run sensitivity analysis.** What happens to cost if volume doubles, or the distribution shifts toward the tail? This tells you how fragile the model is and which assumptions to verify with the business owner before committing.

**How to scope a use case (four steps; skipping any produces a commitment that won't survive the next conversation with the business owner):**
1. **Business requirement → capability list.** Name each capability separately ("process insurance claims" decomposes into: extract structured fields, look up policy coverage, route to the right adjuster queue, draft the notification) so each can be assigned an owner.
2. **Capability list → architecture sketch.** For each capability decide where it belongs — Claude, an existing system, or a human in the loop. (This is Module 1's decomposition applied to a specific use case.)
3. **Architecture sketch → boundary conditions.** State where the architecture works and where it doesn't. *Feasibility is a verdict plus the constraints that make the verdict true.* ("Works for documents up to 20 pages but fails for longer" is a boundary condition that must be documented.)
4. **Boundary conditions → scope in the SOW.** The statement of work contains the boundary conditions, so both the dev team and the business owner know what's in and out of scope.

**Technical feasibility via the four AI properties** — a capability check only asks "can Claude do this"; the four properties show *where* the design needs compensating controls:

| AI property | Feasibility question | Where design compensates |
|---|---|---|
| Next-token prediction | Does the task require probabilistic generation, or precision on specific values? Classification/summarization/drafting are probabilistic (model excels); extracting authoritative values (account numbers, policy dates, claim amounts) requires verification against the source of truth. | Generator-verifier loops; code-based evals on extracted values; tool calls to retrieve quantitative data. |
| Knowledge | Does the task depend on information that is rare, contested, recent, or domain-specific — possibly not in training data? If yes, bring the knowledge into the context window; don't rely on the model to supply it. | RAG for stable knowledge; tool calls for live-state data; flagging uncertainty on contested claims. |
| Working memory | Do the inputs fit comfortably in the context window, or does the task exceed it (long documents, multi-document tasks, extended conversations)? | Chunking strategies; progressive context loading; summarization across turns; pipeline architecture for inputs exceeding the context limit. |
| Steerability | Are the instructions specific, concrete, and verifiable? Abstract/ambiguous instructions, long reasoning chains, and precise numeric/logical computation are where the model drifts from intent. | System prompts with explicit output schemas; structured outputs; code execution for numerical precision; evaluator-optimizer loops. |

**Feasibility verdicts:**

| Verdict | What it means | What to document |
|---|---|---|
| Feasible as scoped | The arguments across the four AI properties favor Claude for each capability. The cost model is within the ceiling. The latency p95 is within the SLA. No capability requires a compensating control that changes the architecture. | State the assumptions clearly. Feasible-as-scoped verdicts become infeasible-with-constraints when assumptions change. |
| Feasible with constraints | The design works under specific conditions that must be enforced. The document length must stay under a threshold. The retrieval index must be refreshed on a defined schedule. A human review gate must exist for outputs above a confidence threshold. The constraints are part of the architecture. | Document each constraint explicitly. For each violated constraint, identify the failure mode. The development team needs to know what they are designing for, not just what they are building. |
| Not feasible | At least one capability faces an AI property limitation that cannot be compensated for within the scope and budget. The cost model exceeds the ceiling by a margin that cannot be closed by model tier, caching, or architecture changes. A not-feasible verdict is a correct assessment that saves the engagement from a more expensive failure later. | State which constraint is disqualifying and why. Where a scope reduction would change the verdict, name it and present the business owner with a choice. |

**Business value & ROI mapping** — a feasibility verdict says the system *can* be built; it doesn't say building it is *worth it*. ROI mapping connects the scoped architecture to outcomes in the business owner's language (hours saved, error rates reduced, cycle time shortened, revenue protected). Five pillars keep the conversation in shared language: **efficiency** (same work faster/cheaper), **transformation** (work newly possible), **productivity** (more output per person), **solution cost** (run cost of the system), **performance SLAs** (service levels the deployment must hold). The mechanism is a **baseline vs. projected** comparison in the same unit; value = the difference minus run cost, where the run-cost figure comes directly from the sizing model (so a token-budget or tier change updates both the cost ceiling and the value case together). Built in four steps: (1) name the baseline in a business unit *from the owner's operational data*; (2) predict the post-deployment state in the same unit, *including human-review cost where the verdict requires it* (projecting full automation overstates value); (3) subtract the run cost from the sizing model (recurring only; build cost handled in step 4); (4) state the **payback period** and its **sensitivity** to volume/gain assumptions.

**Common ROI-map errors:**

| Risk | Why it happens and where it shows up |
|---|---|
| The baseline is estimated rather than measured. | When the business owner does not have clean operational data, the baseline gets filled in from intuition. This makes the apparent gain misleading. The error stays hidden until the finance team asks for the source of the baseline number during business case review. At this point the whole case must be rebuilt. |
| The projection assumes full automation when the design requires human review. | A feasibility verdict that requires a human review gate means the labor is reduced, not fully eliminated. The value case often misleadingly models it as eliminated. The gap surfaces in the first operational period after launch, when actual analyst hours fail to fall as far as the business case promised. |
| The run cost is taken from an average rather than the sizing distribution. | Reusing an average token cost instead of the distribution from the sizing model understates the recurring cost, which overstates net value. This concentrates on workflows with heavy-tailed inputs, where a small fraction of large requests drives most of the cost. |

**Cost · Complexity · Risk:** average-token sizing underestimates cost when requests vary — getting it wrong means renegotiating architecture after the contract is signed. A feasibility assessment that skips any of the four AI properties risks missing a design-changing constraint — **working memory is the most overlooked**, since it rarely shows up on small clean dev inputs but surfaces in production. A feasible-with-constraints verdict that isn't documented becomes an infeasible system when the constraints are violated.

**⚠ Watch Out — "the scoping call that skipped the constraints."** The Architect confirmed capability ("we can do that… six weeks") and issued a feasibility verdict *before* gathering three essential constraints — the partner mentioned only two weeks into the build that they process **800 contracts/day**, some **300-page** framework agreements, needing results in **under 30 seconds**. Two lessons from the reconstruction: (1) whether a 300-page contract fits is a **model-tier decision**, not a settled assumption — a 1M-token window handles it without chunking, a 200k window may need a chunking strategy; (2) at 800/day the 30-second latency target is *not* the binding constraint (that's one request every 108s — sequential processing is viable) — at that rate **volume pressures cost, not latency**, and latency is driven by task complexity, model size, and output length. **Rule:** the capability question was answered before the constraint questions were even asked; volume, latency, and input-size are *inputs* to the verdict, and the verdict is only as sound as the constraints gathered before it.

> **Checkpoint — Justify the feasibility call** (name the correct verdict *and* the single load-bearing constraint):
> - **Scenario 1** (professional-services research assistant, 10–40 page reports, 50/week, 24h, $500/mo): **B — Feasible as scoped.** Input size fits the context window, and volume, latency, and cost are all within range at the Sonnet tier; no AI property presents a disqualifying constraint.
> - **Scenario 2** (logistics delay predictor reading carrier emails and writing ETAs to the order-management system, 5,000 emails/day, <10s, $1,000/mo): **C — Feasible with constraints.** The load-bearing constraint is extraction accuracy on a **transactional write**, so it requires a code-based eval on extraction accuracy plus a human review gate on low-confidence extractions before writing to the system of record.
> - **Scenario 3** (financial-services real-time trading recommendations from current market conditions + a proprietary model, <2s): **A — Not feasible as described.** The load-bearing constraint is the **live-state knowledge gap**: real-time market data requires a tool call to a live feed, and whether that round trip fits inside the 2-second budget must be validated before any feasibility verdict can be issued.

## 4. Enterprise Integration Patterns — identity, auth, data, observability

**Compliance constraints eliminate entry-point options before any other decision**, so entry-point selection comes first; the remaining five layers govern how the integration is built from there. Each layer carries an architectural decision that belongs to the **Architect**, not the implementation team.

**Entry-point selection — which integration to use and when:**

| Entry Point | Use it when | What you trade off |
|---|---|---|
| Direct API | You need full control over how requests are built, how responses are handled, and how errors are managed. Every part of the system is your own code. | You are responsible for building and maintaining retry logic, streaming, tool orchestration, and error handling. The implementation effort is higher than the SDK path. |
| SDK (Python/TypeScript) | You want a convenience layer that handles the basics without giving up control over how the system is designed. The SDK handles the HTTP layer and gives you typed interfaces while leaving orchestration to your code. | Less granular control than the raw API. SDK version upgrades can occasionally change behavior in ways that require code review before deploying. |
| Claude Code | The primary user is a developer, and the task involves writing, reviewing, or navigating code. Not appropriate as the backend for an embedded product. | Not designed for products with multiple users or customer-facing deployments. Claude Code is designed for developer workflows, not as a backend for multi-tenant products; product integrations should use the Claude API, client SDK, or Agent SDK. |
| Agent SDK | You need Claude to act across multiple turns inside your own product, with your application controlling the surrounding workflow. The Agent SDK runs a managed loop, handling iteration, tool execution, and termination. Available in Python and TypeScript. Not the right choice when a single request and response is sufficient, or when the task does not require multi-turn reasoning over tools. | The managed loop gives up fine-grained control over each iteration step. If your use case requires custom logic between turns, a raw API loop gives you that control at the cost of building and maintaining the loop yourself. |
| MCP (Model Context Protocol) | You are connecting Claude to existing tools or internal services and want a standard way to manage those connections without mixing them into your orchestration logic. MCP keeps the integration layer separate from the orchestration layer. | MCP adds a protocol layer between Claude and your tools, which makes debugging tool calls more complex than direct function calls. |

**Security & compliance at the integration layer.** Module 1 established that regulations (HIPAA, GDPR, FedRAMP), attorney-client privilege, and data-residency requirements eliminate entry-point options first. *This is not legal guidance — work with your own legal/compliance team.* The **constraint-to-integration matrix** extends that analysis from entry-point selection to full integration design:

| Constraint | Where it runs (Route) | How it connects (Integration pattern) | Who it trusts (Identity) | What it handles (Data handling) | What it logs (Observability) |
|---|---|---|---|---|---|

Work through the constraints **in order**: identify the governing regulation/policy → determine which entry point and route survive → choose the integration pattern that fits → document the identity, data-handling, and observability requirements that follow. (These sections don't address ZDR use cases.)

**The five integration layers every enterprise deployment decides** (compliance first — it eliminates routes and entry points before the rest):

| Layer | The architectural decision | What breaks when it's wrong |
|---|---|---|
| Compliance and regulated-industry constraints | Which delivery routes and entry points survive the governing constraint? BAA coverage, FedRAMP authorization, data-residency pinning, and approved-vendor lists each eliminate options before the rest of the design begins. | The integration is built on a route that fails the next legal or security review. The cost of redesign at that point is the time already invested plus a new architecture from scratch. |
| Identity and SSO | Where does the user identity boundary sit relative to the Claude integration point? Who is the user in the context of a Claude call, and how does that identity get passed into the prompt safely? | When user identity is not passed into the prompt correctly, Claude cannot scope its responses to what that user is authorized to see. Identity passed as a raw field in the user message is manipulable. Server-side injection removes that risk. |
| Authorization and policy | Which capabilities does this user or role have? What data can they access? The authorization model that governs your existing systems needs to govern the Claude layer as well. | A Claude integration that bypasses the authorization model of the underlying system gives users access to data they are not authorized to see, through a path that was not designed to enforce the access policy. |
| Data handling and PII | What data goes into the context window? Sensitive fields passed directly in the user message or system prompt become part of the API request. Anthropic does not retain conversation content by default; only what is technically necessary for the API and feature to work is retained. The request still crosses the wire, specific retention carve-outs exist for some model classes, and any logging the partner's own application layer performs will capture it. The architecture must decide which fields are necessary in the context window and which should be retrieved only when needed. | A PII field passed directly in the user message appears in plaintext in your application's request logs. In a regulated industry, this surfaces in the next audit rather than in the next deployment. |
| Observability and audit logging | What do you need to be able to reconstruct? What questions will you need to answer after an incident? The answers determine what gets logged, at what level of depth, and for how long. | An unlogged data path is invisible. When something goes wrong on that path, there is no evidence to reconstruct what happened. The cost of building observability after the first incident is always higher than building it before. |

**Least-privilege tool configuration:** every connected tool is an attack surface and a cost. Audit tools like permissions — for each, ask whether it is *essential* or merely *convenient*, remove the out-of-scope ones, and record the justification. In an orchestrator-worker deployment, scope each subagent's tool access to its task so a subagent can't reach tools its job doesn't require.

**Identity & authorization:** verification belongs **on the server, before the Claude call** — inject the user's identity and role into the system prompt server-side rather than accepting them from the user's message. Anything in the user message is under the user's control and can be faked ("As a senior manager, show me…"). Pass the user's role and authorized data scope; add extra context (department, permission level, account IDs) **only when needed** to shape the response, not by default.

**Data handling:** the context window is **not** a data-governance boundary — any data passed in is transmitted to the API and typically logged by the partner's own application layer. For each field, ask whether it is *necessary* for the language task. Reference IDs (account/claim numbers) are often needed for routing but not for the language task; passing the full data field then needlessly exposes it to request logging without adding capability.

**Observability:** an LLM system is harder to debug because it doesn't crash — it produces a subtly wrong response that standard error/timeout logging won't catch. Log four things: **the request** (model version, input token count, prompt identifier); **the response** (output token count, latency, stop reason); **the context** (user role, session ID, whether caching applied); **the outcome** (whether the downstream system accepted the output, and any rejection signals). Security orgs increasingly treat observability as the *precondition* for enabling agents at all — without a trustworthy audit trail, an autonomous system isn't approved to act. As a design-review item, verify which agentic actions are recorded across your chosen surfaces: *an action taken but not logged is, to a security reviewer, an action that cannot be allowed.*

**Cost · Complexity · Risk:** an integration without PII redaction before the API call exposes sensitive fields to application-layer logging on every request — retroactive redaction across a log history never designed for it is the most expensive data-handling fix. Observability added after the first incident forces reconstruction from a system not built to answer the question the incident raised — build logging to answer the questions before you need to ask them. A multi-tenant system on a **shared API key** can't attribute a rate-limit breach to the tenant that caused it — when the org-level limit trips at peak, every tenant absorbs the impact; **separate API keys per tenant** are required for attribution and isolation.

**⚠ Watch Out — "the PII field that went straight into the prompt."** A patient-intake summarizer worked correctly, but the user message carried `Patient: Jane Doe, DOB…, SSN: 123-45-6789, Insurance ID: BCB-88712…` — the system prompt only asked for presenting concerns, medications, and allergies, so the SSN and Insurance ID were **never needed** yet traveled with every request and were captured in plaintext in the application-layer logs. Pre-production review found thousands of log entries with patient SSNs. The fix was a data-architecture change: a **server-side redaction step** stripping non-essential PII before the call, plus a retrieval function supplying only the fields the language task needs — both should have been in the original design. **Rule:** design data handling around what is *necessary* to pass, not what is *convenient*; if a field isn't required for the language task, it doesn't belong in the context window.

> **Checkpoint — Critique the integration diagram** (multi-tenant SaaS customer-service agent; select every integration problem):
> - **Problems:** (1) Claude Code used as the backend for the customer-facing chat product; (2) a shared API key used for all tenants; (3) a capability check based on "I am a premium customer" in the user message; (4) account number and email passed in the user message and appearing in request logs; (5) the Claude response passed to the downstream CRM with no logging at the integration layer.
> - **Sound (leave unselected):** the server-side authentication layer in front of the API; tenant data isolated per tenant at the storage layer.

## 5. A/B Testing & Observability at Scale

Integration gets Claude into the stack; the next question is whether it performs once it's there. **Observability answers the monitoring question; structured A/B testing answers the improvement question.** Without both you are either flying blind or making changes you can't measure.

**Structured A/B testing.** Same structure as any experiment — hypothesis, treatment, control, metric, sample size — but LLM outputs are **probabilistic**, so results are noisier and interaction effects harder to control. The hypothesis must be specific and testable: *"Replacing the instruction to summarize with an instruction to extract the three most important action items will increase task success rate by at least 5% without degrading response latency p95"* names the treatment, metric, success threshold, and constraint. ("The new prompt is better" fails — no treatment, no metric, no threshold.)

| Component | What it requires | What goes wrong when it is missing |
|---|---|---|
| Hypothesis | A specific, falsifiable statement naming the treatment, the expected direction of the primary metric, and any constraints on secondary metrics. | Without a hypothesis, any result can be interpreted as a win. You can always find a metric that moved in the right direction if you look at enough of them after the fact. |
| Treatment and control assignment | Random assignment of requests to treatment (new version) or control (current version). Assignment must be consistent for a given user or session to avoid contamination. | Non-random assignment means the groups are not comparable. If the treatment group happens to receive more complex queries, an apparent win may be an artifact of input distribution. |
| Primary metric | A single metric defined before the experiment runs. Task success rate, cost per completion, latency p95, or user satisfaction proxy. Choosing the metric after seeing the results is outcome-shopping. | An unspecified primary metric turns an experiment into a retrospective correlation, which is a much weaker basis for a decision. |
| Sample size | Calculated from the minimum detectable effect, the baseline metric value, and the required confidence level. For LLM systems, the variance in outputs is higher than for deterministic systems, which means the required sample size is larger. | An underpowered experiment produces results that cannot distinguish a real effect from noise. A team that runs until they see what they want will find what they were looking for, whether it is real or not. |

**Reading results without overclaiming.** Statistical significance means the result is unlikely to be chance *given the sample size* — whether it's **large enough to matter** is a separate question. Two questions before declaring a winner: (1) is the effect large enough to justify the operational overhead of maintaining the new version? (2) did any **secondary metric** degrade? (A change that improves task success but raises cost 30% may not be a net win.) LLM experiments add a failure mode classical tests lack: **interaction effects** between the treatment and specific input types — a change that helps typical inputs may hurt edge cases that are rare in the test period but frequent in a future seasonal spike, so **test-period/input-distribution alignment** matters more here than in most software contexts.

**Shadow testing** — validate a change before any user sees it. Run the new version in parallel, send it a copy of live requests, but serve every user the *current* version's response; the new version's outputs are logged and scored offline. The deployment decision is made before a single user sees the new version. **Choosing between the two:**
- **Live A/B test** when the deployment can absorb a small, bounded exposure to a worse version *and* traffic is high enough to reach significance in a reasonable window. Payoff: you measure against real behavior, including downstream signals (did the user accept the answer, follow up).
- **Shadow testing** when a single bad output carries too much risk, or traffic is too low to support a live split before the change is needed. Cost: loss of downstream signal — scoring relies on an offline rubric or golden answers. For regulated deployments, where exposing users to an unvalidated change may not be permissible at all, shadow testing is often the *only* acceptable way to validate.

**Observability at scale** answers four questions — what is the system doing, how well, when did it change, why — each needing a different instrumentation layer:
- **Request-level tracing:** every request produces a trace (model, model version, input/output token counts, latency, stop reason, tool calls). The raw material for everything else.
- **Metric aggregation:** cost per request, latency p50/p95, task success rate (where the downstream system gives an acceptance signal), error rate by type. **Per-request decomposition is critical** — aggregate metrics can look healthy while a small fraction of requests consumes most of the budget.
- **Anomaly detection:** threshold alerts on the metrics that matter (a cost spike >150% of the 7-day average; a p95 crossing the SLA). **Model drift** (gradual change in output distribution over time) is hard to catch with threshold alerts and needs periodic distribution comparison.
- **Change attribution:** when a metric moves, distinguish **model drift** (behavior on stable inputs changed), **data drift** (input distribution changed), and **model-update effects** (the version changed and behaves differently on existing inputs). Different causes, different mitigations — mixing them produces the wrong fix.

**Failure taxonomy** (instrumentation says a metric moved; diagnosis says what *kind* of failure moved it): **prompt failure** (ambiguous/underspecified instruction — fix the prompt, not the model); **hallucination** (confident, fluent, ungrounded content — fix with grounding via retrieval/tools/verification, not stronger instruction); **model mismatch** (wrong tier for the task, or swapped without re-eval — fix model selection, gated by an eval); **orchestrator-workers failure** (a recoverable subagent failure looks different from an unrecoverable orchestrator failure — attribution needs a trace spanning both).

**Discernment** (one of the four AI-Fluency competencies) applied to production: the habit of classifying each output as *acceptable, needs revision, or needs override* and feeding that judgment back into evals and monitoring. A team without Discernment watches metrics move and never asks whether the underlying outputs were actually good.

**Connect observability to business value:** funders read a KPI dashboard, not request traces. Build a **translation layer** at design time mapping technical metrics to business metrics (task success rate → first-contact resolution; latency → handle time). Build it when the system is designed, not after the first business review — otherwise the first review's question about what's driving handle time requires retrospective reconstruction instead of a live query.

**Cost · Complexity · Risk:** running an A/B test without pre-specifying the primary metric means you can always find a result you want, and underpowered experiments produce false positives — you ship a version no better than what it replaced and absorb its full operational overhead. Instrumentation added after the first incident can't answer the root-cause question from existing logs — the incremental cost of building it correctly the first time is lower than retroactive reconstruction. An LLM system with **aggregate-only** metrics can look healthy while a small fraction of requests consumes most of the budget and produces wrong outputs — aggregate metrics catch obvious failures, **per-request decomposition** catches the non-obvious ones.

**⚠ Watch Out — "the 50-session winner that wasn't."** A team ran a revised system-prompt instruction against 50 sessions vs. 50, saw task success 68% vs. 62%, declared a winner, and deployed — two weeks later the new version settled at 61%; the apparent 6-point gain was gone. Three problems, any one fatal: (1) **sample too small** — a 6-point difference on a high-variance metric needs hundreds per group; at 50 the difference was within the noise floor; (2) **input distribution not controlled** — the treatment group happened to hold fewer edge cases; (3) **primary metric not pre-specified** — they compared task success because it moved, and would have looked elsewhere if it hadn't. **Rule:** an underpowered experiment with after-the-fact metric selection produces *confirmation, not evidence* — the noise looked like signal because the sample was too small to tell them apart.

> **Checkpoint — Place on the experiment-design plane** (axes: expected **effect size** × **confidence requirement** driven by stakes; the *Large effect · Low confidence* zone is unused). Placements:
> - **A** (minor wording change to a clarification message in a low-stakes FAQ chatbot) → **Small effect · Low confidence**
> - **B** (prompt-architecture change for a medical intake summarizer where an error could delay treatment) → **Large effect · High confidence**
> - **C** (adding a new classification category to a routing model expected to capture 30% of volume) → **Large effect · Moderate confidence**
> - **D** (switching Sonnet→Haiku on a simple formatting task to save cost without degrading quality) → **Small effect · High confidence**
> - **E** (a small change to the retrieval prompt in a RAG system at 200 requests/day) → **Small effect · Moderate confidence**
> Correct placement sets the experimental posture, which sets the minimum sample size.

## Exercise — define the evaluation framework (with model answer)

**Brief:** A regional insurer deploys a Claude system that reads a submitted claim, **extracts structured fields** (claimant, policy number, loss amount, date of loss), **summarizes** the narrative for an adjuster, and **flags** claims that may warrant fraud review. It must respond within a few seconds, stay within a per-claim cost, **never leak one claimant's data into another's summary**, and **never auto-deny a claim.** For each of five dimensions, give the metric, grading method, and reason.

**Model answer:**

1. **Accuracy, field extraction — Code-based eval.** The expected values (claimant name, policy number, loss amount, date of loss) are known and verifiable by exact or schema match. No interpretation required; a function checks the output against ground truth.
2. **Latency, response time — Code-based eval.** Latency p95 is a number; the check is whether it falls below the target. No judgment involved.
3. **Safety, summary faithfulness and no auto-deny — Two methods.** Code-based eval for the deny action (binary — either a denial was issued or not). LLM judge for summary faithfulness (whether the narrative accurately represents the source claim without fabrication is an interpretive task a function cannot encode).
4. **Security, no cross-claimant data leakage — Code-based eval.** Leakage can be checked by scanning each summary for identifiers that appear in any input claim other than the one being processed. Deterministic check, no interpretation needed.
5. **Cost, per-claim spend — Code-based eval.** Cost is a numeric value derived from input tokens, output tokens, model tier, and whether prompt caching applies. The check is whether it exceeds the ceiling.

*Self-assessment guidance:* The distinguishing moves are **splitting Dimension 3** into code (the action) and judge (faithfulness), and **keeping Security in code** because the check is deterministic despite the high stakes. Common errors: using a judge for field extraction (it's deterministic — code handles it), and treating the auto-deny check as interpretive (it's binary — code handles it). *Use code where the behavior is unambiguous (known value, binary check, numeric threshold); use a judge where correctness requires interpretation.*

## Cumulative exercise — Production Readiness Builder (with model answers)

**Brief:** A 600-person management-consulting firm wants an internal knowledge assistant that retrieves excerpts from past engagement reports, answers questions about firm methodologies, and drafts first-draft RFP responses using past work. **Corpus:** 12,000 documents, 5–80 pages each. **Peak usage:** 800 requests/day during active engagements. **Ceiling:** $3,000/month. **Latency:** p95 under 8s. The firm has existing SSO (e.g., Okta) and a document-management system (e.g., SharePoint); several documents contain client-confidential, NDA-bound information.

**Decision 1 — Eval strategy.** Code-based eval: **schema compliance on extracted citations** (document name, page number, section). Model-based eval: **relevance and appropriateness of the draft response to the RFP.** Golden dataset: built from past RFPs with **redacted client names**, sourced from historical engagements. Client-confidential documents are **excluded from the eval set unless the client has given explicit approval.**

**Decision 2 — POC-to-production checklist.** Cost model: 800 req/day × 30 = **24,000 requests/month**. System prompt ~2,000 tokens (methodology overview + instructions) + retrieved context ~3,000 + query ~200 = **~5,200 input tokens**; output ~600 tokens. At Sonnet tier with caching on the stable system prompt, projected cost is within range. **These are flat averages** — the projection assumes requests cluster near the mean with no heavy tail. Because the corpus runs 5–80 pages, retrieved-context size is likely **bimodal**, and a tail of large excerpt requests understates input cost on a flat-average model; the within-ceiling verdict holds under the assumed distribution and should be checked with the **sizing-cluster sensitivity analysis** before it's relied on. Reliability: **fallback chain from Sonnet to Haiku** for latency spikes. Most critical failure mode: **retrieval quality drift** as documents are added — inconsistent indexing degrades retrieval precision and draft quality with it.

**Decision 3 — Use-case sizing and feasibility.** **Working memory:** no individual document (up to 80 pages, ~29,000 tokens) exceeds the current Claude context window of 1M tokens on most current models — a single max-length document fits well within the window and is *not* a working-memory constraint on its own. The **binding constraint is corpus scale**: the full 12,000-document corpus (average ~14,600 tokens/doc across the 5–80-page range, ~**175 million tokens** total) far exceeds any context window and can't be loaded simultaneously — **this is what drives the RAG architecture** (chunking exists for individual documents but is not the load-bearing constraint here). **Knowledge:** the firm's proprietary methodologies are not in training data, so the model can't supply them from memory — mitigation is **retrieval**: index the methodology documents in the same RAG layer as the engagement reports and surface them at query time. The system doesn't need Claude to *know* the methodologies, only to reason over methodology excerpts the retrieval layer puts in front of it; the constraint is that **retrieval quality must surface the right content** (track retrieval precision on methodology queries as a separate metric in the eval suite and in production observability). **Verdict: Feasible with constraints.** All four axes are addressable — working memory resolved by the RAG layer, knowledge gaps resolved by indexing methodology docs, steerability met by the system-prompt structure and RFP output schema. **Load-bearing boundary condition: retrieval index coverage and freshness** — the system works only while the index contains the relevant methodology/engagement documents and is kept current as the corpus changes; if the index is incomplete, documents are added without indexing, or it drifts out of sync with the document-management system, the knowledge mitigation fails and responses omit or misrepresent firm methodology. **That condition must be documented as an explicit operational constraint in the SOW.**

**Decision 4 — Integration pattern selection.** **Identity:** the Okta token is verified server-side; user role and authorized document sets are **injected into the system prompt by the server**, not supplied by the user. **Client-confidential handling:** documents tagged confidential in SharePoint are retrievable **only by consultants whose role includes the relevant client engagement** — the retrieval layer enforces this access control *before* passing content to Claude. **PII:** client names are replaced with anonymized identifiers before a document enters the context window. **Observability:** log model version, input token count (with caching hit/miss), **retrieval precision per request** (against the grounding documents), and output token count; log user role and session ID at the context layer; capture the consultant's **acceptance or revision of the RFP draft** as the outcome signal; alert on p95 crossing 8s and on retrieval precision dropping below threshold.

**Decision 5 — A/B testing posture.** **Hypothesis:** the new retrieval configuration will increase RFP draft task success rate (measured by consultant acceptance without major revision) from **70% to at least 75%**, without increasing latency p95 above 8s or cost per request by more than 10%. **Sample size:** detecting a 5-point improvement at 70% baseline with 80% power and 5% significance requires **~1,500 sessions per group**; at 800 requests/day split evenly, **~4 days** — feasible. **Input distribution control:** ensure treatment and control have similar distributions of RFP complexity (proxy: document length and number of source documents retrieved); segment by RFP type if possible.

*Strong answers name specific numbers (cost model, ~175M-token corpus, 1,500 sessions/group, ~4 days) and tie each decision to the next: the sizing model feeds the cost ceiling, the feasibility boundary condition (retrieval coverage and freshness) feeds observability, and the eval feeds the A/B primary metric.*

## Glossary

The key terms used across the module, alphabetical.

- **5xx errors** — HTTP status codes (500–599) indicating a server-side failure to fulfill an otherwise valid request. Examples: 500 (Internal Server Error), 503 (Service Unavailable), 529 (Overloaded Error). Usually transient and resolvable with retry and backoff; distinct from 4xx codes, which indicate a client-side problem.
- **BAA (Business Associate Agreement)** — a contract required under HIPAA between a covered entity (or business associate) and a vendor that handles PHI on its behalf, specifying the safeguards the vendor applies. For Claude deployments, BAA coverage is **configuration-specific**: the same surface may be BAA-covered on one route and not another. Check coverage by configuration, not by product.
- **Caching** — stores reusable prompt content so the system doesn't reprocess it on every request. Most effective when the system prompt is long and stable, reducing both token cost and latency; the response you receive is identical to what you'd get without caching.
- **Circuit breaker** — a reliability control that monitors the error rate on a downstream dependency and, when errors exceed a threshold, blocks further requests to it for a cooldown window so one degraded component doesn't consume the caller's capacity. Sits at the **service boundary**, distinct from retries (close to the API call) and fallback chains (in the orchestration layer).
- **Data-residency pinning** — configuring the integration so model execution happens in a specified region, typically to satisfy sectoral regulations or internal policy. Implemented at the delivery-route level on CSP-mediated integrations. The pin must be set at the integration layer and **verified at request time**, not assumed by the entry-point choice alone.
- **DPA (Data Processing Agreement)** — a contract between a data controller and a data processor defining how personal data may be handled on the controller's behalf: processing scope, security obligations, sub-processor terms, and breach notification.
- **Eval** — a structured test set that measures whether a model performs well enough on a defined task. It pairs inputs with expected outputs or quality criteria, runs them against the model, and produces a score comparable across model versions, prompts, or configs. Evals are how teams decide whether a change is an improvement or a regression before it reaches production.
- **Exponential backoff** — a retry strategy where, after a failed request, the system waits before retrying and each successive wait is longer than the last, typically doubling each time.
- **GDPR (General Data Protection Regulation)** — the EU regulation governing processing of personal data of individuals in the EU/EEA. Establishes lawful-basis requirements, data-subject rights, controller/processor obligations, and fines up to 4% of global annual turnover.
- **Generator-verifier loop** — a two-stage pattern where a model-generated output is checked by a second pass before downstream use. The verifier may be a deterministic code-based check (schema validation, comparison against an authoritative value) or a second model call scoped to evaluation. Used as a compensating control where the task requires more precision than single-pass generation reliably provides.
- **Hallucination rate** — the percentage of responses in which the model invented, inferred, or stated information not supported by the input, source data, or allowed logic.
- **Live state** — data that changes during a conversation or process: order status, inventory count, price, calendar slot, current session. Distinct from static reference material because the correct answer at 10:00 a.m. may be wrong by 10:05. Systems needing live state require a **direct lookup against the source of truth**, not a stored snapshot.
- **Median latency** — the time to complete the middle request in the distribution (50% faster, 50% slower). Also called p50 latency.
- **p95 (95th-percentile latency)** — the latency value below which 95% of requests complete, with the slowest 5% above. Used as a production design target because SLA breaches and user abandonment are driven by the slow tail, not the median.
- **PHI (Protected Health Information)** — individually identifiable health information held or transmitted by a covered entity or business associate under HIPAA. Processing PHI requires a BAA with any third party that handles it.
- **RAG (retrieval-augmented generation)** — a pattern where a knowledge corpus is chunked and indexed in preprocessing, and at query time the chunks most relevant to the input are retrieved into the model's context. Suited to static/slow-moving knowledge (manuals, internal docs, regulatory text); **not** suited to live transactional state, where retrieval returns a possibly-stale snapshot and a tool call to the system of record is correct.
- **Rate limit** — a server-enforced cap on requests within a time window. When exceeded, the server rejects further requests (typically HTTP 429) until the window resets. Indicates throttling rather than failure; a transient condition that resolves with backoff.
- **Regex** — regular expression: a rule-based pattern used to find or validate text matching a specific format (email addresses, phone numbers, SSNs, credit-card patterns).
- **Schema** — the required structure, format, and rules for the output: what fields must appear, their data types, allowed values, and how the response is organized.
- **SSO (single sign-on)** — an authentication arrangement where a user signs in once to a central identity provider and gains access to multiple downstream applications without re-authenticating.
- **Structured fields** — outputs that must be populated in a defined format (customer name, invoice number, date, amount, policy ID). Discrete data elements, not free-form narrative.
- **Timeout** — a failure mode where a request doesn't receive a response within the configured wait period and is terminated. Typically caused by transient server load, network latency, or a stressed downstream dependency, not a permanent fault.
- **Tool use** — the capability that lets Claude call external functions, APIs, or services during a response instead of only generating text. The model decides when to invoke a tool, what arguments to pass, and how to use the result. Turns Claude from a text generator into a system that can read files, query databases, search the web, or act in other software.
- **Transient error** — a temporary failure expected to resolve on its own without a permanent fix; retrying the same request after a short wait will likely succeed.

## Recap — five takeaways

1. **Evals as acceptance criteria** — write the eval suite before production code; keep the golden dataset current with every system change; use the eval as the gate for every model swap or prompt revision.
2. **POC to production** — estimate cost and latency at production volume before committing to architecture; build retries, fallback chains, and circuit breakers into the initial design; name the failure mode specific to your architecture type and document the mitigation.
3. **Use-case sizing and feasibility** — run every new use case through the four AI properties before issuing a verdict; state it as *feasible as scoped, feasible with constraints,* or *not feasible*; document the load-bearing boundary condition for every constrained verdict.
4. **Enterprise integration patterns** — enforce identity server-side; pass only the minimum necessary data into the context window; build observability instrumentation at design time, not after the first incident.
5. **A/B testing and observability** — identify the primary metric and sample size before running any experiment; at scale, separate per-request observability from aggregate dashboards; build a translation layer mapping technical metrics to the business metrics the stakeholder cares about.
