Probe 3 · How does the agent know it's right?

AGT-031 · AGT-009 · promotion gates

This is the probe. Every harness Keyur has built emits answers. SOPs, recommendations, natural-language SQL. PR-3's agents emit code and infrastructure. You evaluate an answer with a judge and a rubric. You verify code by compiling it, running the tests, and diffing behavior. Anyone who has done real codegen harness work knows the compiler is the best evaluator they will ever get for free. Whether he reaches for it unprompted tells you more than anything else in the call.

SOP is Standard Operating Procedure. In a regulated plant it's the written, step-by-step procedure an operator follows, and in life sciences the FDA cares what's in it. That's why his system has human approval bolted on. You can't ship an unreviewed one. Worth knowing so you can follow up instead of nodding.

Open with, about whatever project he picked

So before anyone actually looked at it, did the system have any way of telling whether what it produced was any good?

Then the one that matters

Here's what I'm curious about. With a document, someone has to read it to know it's right. If the agent had been writing code instead, would you check it differently?

You're listening for one word. Run. Build it, compile it, run the tests, diff it against the old behavior. If he gets there quickly and without being led, he has done this. If he keeps reaching for judges and rubrics, he hasn't. You don't need any codegen background to hear which one you got, which is why this question names no tooling.

Then keep going. This is where the gates actually are.

Ask all four, in this order

Say the agent generates a CDK template, or a source file it has rewritten. Walk me through every check that artifact has to pass before a person ever sees it.

How would you tell the difference between output that's broken and output that's wrong? Something that won't compile, versus something that compiles fine and does the wrong thing.

What would you measure on the artifacts themselves, so you'd know whether the agent was getting better or worse month to month?

And when one of those checks fails, what happens to that artifact? Retry it, park it for a human, kill the whole run?

The first two questions find the instinct. These four find out whether he'd actually build anything, and they're deliberately concrete, because "how do you approach governance" gets you a paragraph of nothing while "walk me through every check before a person sees it" gets you either a real pipeline or a blank.

Broken versus wrong is the sharpest of the four. The naive answer only covers broken, which the compiler catches for free. Wrong compiles cleanly and quietly does something else, and catching it needs a behavior comparison or a test that already existed. Someone who has built a transformation pipeline reaches for that distinction on their own.

He may well not have done any of this, and that's expected. Score the reasoning, then cross-check it against Probe 4. If he describes an elaborate pipeline here and then has no story about anything ever going wrong, the pipeline was designed rather than earned.

Gate or prompt is the whole distinction, and it's the sentence that connects this probe to the last one. A prompt is a request the model can talk its way past on an input nobody tested. A gate is code that fails.

So this probe is the evidence for whatever he described in Probe 3. A structural fix confirms it. A prompt tweak means the verification pipeline he sketched was aspirational, and you should mark that earlier answer down accordingly.

Pivot bank

When he opens a door, walk through it

The probes above are the spine. These are for when he volunteers something and you want to go deeper without losing the thread. The first three are scenarios rather than recall questions, so he can't answer them from having read the docs. They're also the kind of question that's enjoyable to answer, which matters, because a screen that feels like a conversation gets you more than one that feels like a quiz.

Scenario · the obvious answer is wrong

An agent runs fine for the first six or seven tool calls, then starts picking wrong tools and giving worse answers. Nothing changed in the code. What do you check first?

Everyone goes to the tool descriptions. The usual cause is tool results piling up in the window and crowding out the instructions, and in production those results run several times bigger than anyone's test fixtures. You can't reason to that from documentation. He either hit it once or he didn't.

Scenario · probably happened to him

Retrieval works fine in testing. In production it misses whenever someone searches by a specific part number or error code. What's going on?

Similarity search is semantic, so an exact identifier loses to a chunk that reads closer but says nothing useful. Wants a keyword pass alongside the vector one. His users are plant engineers searching by tag numbers, so if he built real retrieval for them he has hit this wall.

Scenario · specific symptom, non-obvious cause

You've built an LLM judge to score outputs and it gives almost everything a 7 or an 8. What's wrong with it?

Models settle on a safe middle number when you ask for a bare score. Wants reasoning before the score, and calibration against cases a human already labeled. "Make the prompt stricter" is the wrong instinct.

If he talks about tools or MCP

Say you've got five tools registered and the agent keeps reaching for the wrong one. Walk me through how you'd debug it.

Wants descriptions rather than the model. An exclusion sentence, when not to use each one. Knowing that registering everything just in case makes selection worse. Docs-reader says "it uses the description." Someone who's debugged it says "I'd check whether two of them say the same thing."

If he mentions fan-out or parallel workers

When you split work across workers, how did you know nothing got quietly dropped? What did one full run cost, and what would it cost at four hundred apps?

AGT-002 has to fan out over codebases no window holds. The dangerous failure isn't a crash, it's a worker skipping its unit while the summary reads complete. And the cost question is the one to weight, because almost nobody offers a real number unprompted.

If he talks about context or compaction

What's actually in your compaction prompt? What did you lose the first time you got it wrong?

Wants a summarizer that keeps file paths, decisions and errors. "Summarize the conversation" drops exactly the state the agent needs next turn.

If he cites Bedrock AgentCore

His resume says POC. An honest "it stayed a POC" is a green flag. Inflating it is a much bigger finding than the gap itself.

If he's strong and you have room

If you were building AGT-031, transforming source against ORM rules. Rules engine, model, or both? Where's the seam?

Wants: deterministic rules for the known cases, model for the long tail, confidence routing between them. This is the role in one question.

If he mentions LangGraph or frameworks

Wants: loop, context management, checkpointing, retries. Someone who can't answer has never seen underneath the abstraction.

The sharpest way to get him off abstractions. Almost impossible to answer about a system you were shown rather than one you built.
