Take two decisions first

Roughly ninety raw bullets collapse into 23 decisions, mostly because the same question keeps getting restated against a different prompt. Two of those 23 sit underneath everything else, and both are worth settling before the room touches anything narrower.

F2, what the word "dependency" covers, changes the answer set in 11 of the 20 walkthroughs. F1, how a repeated work item number resolves, changes which item the agent answers about in 8 of 20. Neither one is a data question. They are business definitions the data cannot settle on its own, and several of the remaining decisions read differently once they are closed.

Finding the right work item

F1

Which item does the agent answer for when a number names items in several orgs?

8 of 20Product owner

F01.1  F01.2  F02.1  F06.2  F07.1  F07.2  F08.1  F08.2

A work item number is not unique. 382 of the 46,566 numbers that carry any dependency link carry them in two orgs, and no number reaches three. Every tested case resolved by luck of the data rather than by rule, because only one org's item happened to carry a dependency link and the unscoped walk came back with a single row. F06.2 and F08.1 resolve the same three-way collision two different ways and both land on the same item, which hides the fact that the agent has no rule at all.

Options on the table
  • Ask the user for the org before answering.
  • Answer once per org and let the user pick.
  • Walk the links unscoped and answer from whichever item carries dependency links (F06.2).
  • Match the prompt's own qualifier against the area path (F08.1's "Trading IT / Allegro").

Nobody has measured how often several same-number items each hold dependency links, and that is the number deciding whether this needs a disambiguation step at all. F07.2, F08.1 and F08.2 each resolved their collision through the prompt's team qualifier, and all three flag the same gap. A qualifier that matches two candidates' paths leaves the number ambiguous again.

Left openThe agent can answer confidently about the wrong team's work item.

F3

Which field does a prompt term get searched in?

4 of 20Data SME

F03.2  F05.2  F09.1  F09.2

The schema states no rule here, and the field choice changes what the agent finds rather than just how much of it. "Process mining" returns 214 unrelated rows in TITLE and misses the requester, but resolves correctly against the area path. "SAP PO" is useless in TITLE, at 5,016 rows across 273 teams, and works in the area path. The squad names Bengals and Ravens sit in both fields with very different coverage, 677 items by title against 17,951 by area. "Brazil Tax Reform" resolves to no usable set in any field we checked.

The distinction the working doc draws is worth keeping. A title says what one work item does, whereas an area path says what type of work a team does. That is close to a rule already, and it is definitely the one I would put in front of the SME to confirm or reject.

Left openThe same prompt succeeds or fails depending on which field the generated SQL happens to hit.

F4

Can recall depend on the user's exact wording?

5 of 20Product owner

F02.2  F03.2  F05.1  F05.2  F09.2

Five separate walkthroughs found real work that the prompt's own wording cannot reach, and each one misses it a different way.

  • F02.2 spells the initiative "Brazil Tax Reform" in the prompt while the linked teams spell it "Brazilian TAX Reform". Widening to %BRAZIL%TAX% returns 32 rows against the prompt's 10, and two of the extras are items the initiative already links to.
  • In F03.2 and F09.2, Celonis is the process mining product, and 331 of its 477 items sit under paths with no "mining" in them, invisible to the %MINING% search.
  • F05.1's subject terms as spelled catch 111 items, which leaves out "NF-e" with a hyphen and "e-billing".
  • F05.2's two prompt tokens cover 8 of the 12 Bengals-to-Ravens links. The other 4 are the same dependency worded as "Refresh ACC tables from Mike's List".

None of these changed a verdict, which is exactly why they are easy to sign off without noticing. What the room has to settle is whether the agent may answer from a wording-sensitive search with no signal to the user at all, or whether it owes them a synonym pass or a coverage caveat.

What counts as a dependency

F2

Which link types does the word "dependency" cover?

11 of 20Product owner

F01.1  F01.2  F02.1  F02.2  F07.1  F07.2  F08.1  F08.2  F09.1  F10.1  F10.2

Rule 4 keeps Predecessor and Consumes From and drops everything else. Every walkthrough counts that exclusion and none of them reads it.

CaseKeptExcluded and never read
F01.11 link70 active: 62 Related, 4 Child, 4 Parent
F01.21 link87 active: 71 Related, 12 Child, 4 Parent
F02.11 Predecessor12: 8 Related, 4 Parent
F02.26 link targets25 on item 1627170

F08.22 predecessors7: 6 Related, 1 Parent, all same-team earlier table work

Every one of those rows carries the same sentence. A reading of "depends on" that includes the parent epic's team would change the answer, and nothing in the data rules that reading out. F07.2 is the sharpest version, given that the prompt literally says "linked dependencies" and the agent returns 2 of the item's 20 links.

There is a second half to this decision, which is the two dependency mechanisms underneath it. Predecessor is 100% same-org and Consumes From is 100% cross-org. F10.1 counts 10,972 out-of-sequence Predecessor links and leaves the 150 Consumes From ones outside the number, and F10.2 does the same. F09.1's aggregate never splits its 192 Predecessor links from its 19 Consumes From ones, so whether late delivery clusters in one mechanism is untested.

Options on the table
  • Dependency link types only, as Rule 4 has it today.
  • Dependency types plus Related.
  • The full link list with the type shown, and the user judges.

Left openEvery answer in the corpus is provisional, because the set it is drawn from is provisional.

4 of 20Data SME

F02.1  F05.1  F05.2  F06.1

Four different exclusions turn up across these cases, and none of them is settled.

Dates and risk

F7

Which date pattern counts as a delay or a risk?

5 of 20Product owner

F01.2  F08.1  F08.2  F10.1  F10.2

Five different date shapes turn up across these cases, and the walkthroughs report them inconsistently. Nobody has ruled on which of them is supposed to count as risk.

  • F08.2 reports a predecessor closing 116 days before its successor and another closing 1 day after, and calls neither one the risky shape. They are not the same failure.
  • F01.2 reports a +1 gap as "no delay" while noting the same pair is an inverted close order, one of the 10,968 F10.1 counts corpus-wide.
  • F08.1 returns predecessor 1929157, still New while its successor is Closed. The Golden Dataset omits it. Nobody has said whether that is mis-sequenced by definition.
  • F10.1 offers three causes for out-of-sequence links, a data-quality issue, a reversed direction, or a link added after the work finished, and no field distinguishes them. FCT_ADO_WORKITEM_LINKS_HISTORY records when a link was created, which separates the third cause from the first two, and no step reads it.
  • F10.2 notes that a null close date on an item in state Analyze means work in progress and on a Removed item means something else. The count treats both the same.

F10.1 flags the blind spot underneath all of it. The count drops any link with a missing close date on either end, and comparing dates cannot detect an out-of-sequence dependency whose predecessor is still open. That is 19,208 links with no successor close date and 13,251 with no predecessor close date.

Left open"Dependency risk" means whatever the query author decided that day.

N1

What is the end-to-end response time budget?

20 of 20Stakeholder

Every one of the twenty walkthroughs raises this, and every one records the same absence. Nobody has agreed a limit.

The measured parts do exist. A keyed lookup on WORKITEM_ID_SOURCE runs about 2 seconds. A LIKE scan of the 6.4M-row item table also runs about 2 seconds. A corpus-wide count joining the 25.3M-row link table to the item table twice runs 3.1 to 5.0 seconds. An org-scoped Azure SQL lookup takes about 13 seconds, and an unscoped one times out.

Step counts run from 2 queries in F06.2 and F08.2 to 6 in F09.1 and F09.2. F09.1 is the worst case on paper, at 6 Snowflake queries of 2 to 5 seconds each plus Azure SQL lookups of about 13 seconds.

F09.2 names the architectural fork that decides the real number. A single-shot generator pays the round-trip cost once, whereas an agent that plans between steps pays it per step. That is the difference between roughly 25 seconds and something well past a minute, and the team should pick against a stated target rather than discover the number in the pilot.

N6

How are timeouts handled, and is the org filter mandatory?

6 of 20Engineering

F02.2  F04.1  F04.2  F05.2  F06.1  F09.2

An Azure SQL lookup with no org filter times out, so the org from the Snowflake step has to carry into the Azure SQL step. That is a hard constraint on query construction, not a preference.

F06.1's Azure SQL attempt times out at 20 to 45 seconds and returns nothing, so trying it buys the wait and no rows. F05.2 is the sharpest case. A LIKE scan for a nickname in Azure SQL free text times out past 120 seconds with or without an org filter, and if Snowflake had not resolved the term first, the agent would have had no working text search left. It has to report that rather than hang.

Running the session

Split the room first. F3, F6, F8, F12 and F13 are data questions the SME can answer from the schema and a few queries. The rest are business definitions, and asking a data SME to rule on what "dependency risk" means produces an answer nobody in the room is bound by.

Then take F2 before anything else. Eleven of the twenty walkthroughs change if the answer to "which link types count" changes, and several of the other decisions read differently once it is settled.

Three items need a measurement before anyone can decide them, so they are definitely worth commissioning now rather than debating in the room: how often several same-number items each carry dependency links (F1), how often current Snowflake items are missing from Azure SQL (N4), and what a question costs in warehouse credits (N2). None of the three takes long to run, and having those numbers on the table turns three arguments into three readings.
